## 一、 面试开场：项目自我介绍（电梯演讲验证版）

**面试官提示：** _“同学你好，看到你的简历上写了一个基于 Raft 的分布式 KV 项目，能简单介绍一下这个项目的整体架构以及你所做的核心工作吗？”_

**口语化回答建议（控制在 1.5 ~ 2 分钟）：**
> 面试官您好，我介绍一下这个分布式 KV 项目。
>
> 这是一个类似 etcd 的强一致性分布式系统，主要解决在这类节点故障的场景下，如何保证数据的安全和高可用。它的**底层架构分为三层**：网络层依赖于我自己手写的一个基于 Reactor 模型的 RPC 框架；中间共识层是我从零实现的一套 Raft 算法（包含选举、日志复用和快照）；顶层的状态机则挂载了一个自行实现的 SkipList 作为内存引擎。
> 
> 在完成基础功能后，我发现**直接照搬 Raft 原理会带来很多性能瓶颈**。因此我做了四个方向的核心扩展：
> 第一，我发现所有的读请求也要走一遍很重的落盘和 RPC，所以我引入了 **ReadIndex 机制**，把读请求的走网络和落盘变成了只依靠心跳确认，让读延迟下降了 50% 以上。
> 第二，原来的网络框架一收到包就去跑 Raft 逻辑，会严重阻塞底层 Epoll。我在中间**引入了一个专用的业务线程池**，把这 IO 密集型和 CPU 计算型做了解耦。
> 第三，为了接近工业级标准，我实现了 **TTL 过期删除**。为了防止全量扫描导致系统出现 P99 长尾毛刺（STW），我用了“惰性删除 + 后台轮询抽样”结合的算法。最后，我还内建了轻量级的 **Metrics 监控**，方便分布式调试追踪。
> 
> 总体来说，这个项目不仅帮我吃透了 Raft 原理，更锻炼了我从网络层到系统架构的全链路调优能力。这也是我非常喜欢的一段工程经历。

## 二、 面试官 Q&A 深度剖析（大类拆解）

### 1. Raft 共识算法与一致性模型 (核心基石)
> **大类说明：** 考察候选人是否真的手写过并理解 Raft 原理，而不是纸上谈兵。重点在于选举、日志一致性的边界条件，以及线性一致性的保障机制。

*   **Q1.1 (基础引入): 简单说说 Raft 中的三种角色及它们之间的状态转换？**
    *   **思考链条：** 角色定义 -> 超时机制触发选举 -> 收发心跳降维。
    *   **回答：** 系统中有 Leader、Follower 和 Candidate。初始时大家都是 Follower；当 Follower 的选举定时器超时没收到心跳，就会自增 Term 变成 Candidate 请求投票；如果拿到集群一半以上的选票，就晋升为 Leader，并立刻开始广播心跳维持统治。若 Candidate 收到其他合法的 Leader 心跳或者更高 Term 的消息，就会退回 Follower。
    
*   **Q1.2 (选举细节): 怎样保证选出来的 Leader 一定拥有最全的已提交日志？**
    *   **思考链条：** 选举的安全性规则 (Election Restriction) -> 投票时的两个条件比对。
    *   **回答：** 在 RequestVote RPC 中，Candidate 必须带上自己本地最后一条日志的 `lastLogTerm` 和 `lastLogIndex`。Follower 收到选票请求后会把自己的这两个值和候选人的比较。比较规则是：**先比 Term，谁大谁新；Term 一样比 Index，谁大谁新**。只有候选人的日志至少和 Follower 一样“新”，Follower 才会投出赞成票。由于任何被 Commit 的日志必定存在于半数以上的节点中，所以新 Leader 如果能拿到半数票，必然包含所有已 Commit 的日志。

*   **Q1.3 (日志一致): 如果网络分区导致旧 Leader 包含一堆没提交的冗余日志，恢复后 Raft 是如何处理这种冲突的？**
    *   **思考链条：** 发现不一致 (PrevLog匹配失败) -> `AppendEntries` 返回 false -> Leader 递减 `nextIndex` 后退 -> 强制覆盖。
    *   **回答：** 旧 Leader 恢复后会收到新 Leader 的心跳并降级。当新 Leader 给它发 `AppendEntries` 时，会带上 `prevLogIndex` 和 `prevLogTerm`。旧 Leader 检查自己同位置的日志，发现打不上（即发生分叉），就会拒绝接收。新 Leader 收到拒绝后，会将发往该节点的 `nextIndex` 递减，不断向前试探，直到找到两者日志完全一样的那个点。一旦找到，新 Leader 就会强行把随后的日志发送过去，将旧 Leader （或者说新 Follower）的错误日志强制截断并覆盖，从而达成最终一致。（*进阶补充：如果想优化逐个递减慢的问题，可以通过返回冲突 Term 的首个 Index 实现批量跳过*）。

*   **Q1.4 (一致性语义): 你的简历里写了“配合 Request ID 保证线性一致性语义”，原生的 Raft 不处理这个会有什么问题吗？**
    *   **思考链条：** 分布式网络重试问题 -> 丢包导致的多次提交 -> 客户端请求去重。
    *   **回答：** 会有“脏写”或重复应用的问题。如果客户端向 Leader 提交了一个指令（例如 X+1），Leader 处理并 applied 了，但是在回复客户端时网络超时了。客户端以为失败了，就会针对同一个请求再次重试。如果不再做防护，状态机就会执行两次 X+1。这打破了一致性。
    *   **最终实现：** 客户端会维护一个单调递增的 Request ID (Client ID + SeqNum)。我的 KV Server 内部维护了一个 Map 记录每个 Client 最近执行过的 SeqNum 与回复。再次遇到相同的 ID 的操作时，系统直接从查到缓存的回复结果返回给客户端，不再推入跳表执行。

*   **Q1.5 (拓展追问): 为了支持这个 Request ID 去重 Map，如果 Client 越来越多，内存撑爆了怎么办？**
    *   **思考链条：** 内存淘汰 -> LRU / 定时清理。
    *   **回答：** 会有 OOM 风险。工业界做法是（在我的项目中也有预留逻辑或者思路）：引入一个 LRU 机制淘汰太久远的 Client Session，或者是只保留每个 Client ID 对应的“最老的活动未完成的 SeqNum”，所有比这个小的 SeqNum 请求直接丢弃。

### 2. 读写链路优化：ReadIndex 机制 (性能爆点)
> **大类说明：** 面试中最具含金量的性能调优考察。重点验证你是怎么识别“写放大”瓶颈，以及解决这个瓶颈的算法逻辑有没有漏洞。

*   **Q2.1 (场景痛点): 为什么你说纯原生 Raft 的读请求延迟很高？具体是哪里耗时？**
    *   **思考链条：** 读写不分家 -> I/O 长链路 (本地落盘 + 网络广播RTT + 落盘ACK)。
    *   **回答：** 在原生 Raft 下，即使是个单纯的 Get 请求也会被生成一条 Log Entry。这条日志要先写入 Leader 的状态持久化盘（磁盘 IO），然后发向所有节点（网络 RTT），多数节点收到后也要落盘，最后 Leader 确认后返回状态。在读多写少的场景里，为了读操作导致大量的无用日志落盘，这就是严重的“写放大”，导致延迟极高。

*   **Q2.2 (机制推演): 那什么是 ReadIndex 优化？它的详细流程是怎样的？**
    *   **思考链条：** 记录快照点 -> 确认领导权 -> 等待状态机应用。
    *   **回答：** ReadIndex 就是绕开磁盘日志，但依然保证线性一致读的设计。主要经过三步：1. Leader 收到读请求，记录下当前的 `commitIndex`，称为 `readIndex`；2. 为了防止当前 Leader 其实已经被孤立在少数派（产生脑裂）导致它自己不知道，它必须发起一轮心跳 RPC 或等待下一次常规心跳，只要收到多数派回应，证明自己还是真 Leader；3. 随后，Leader 死等（挂起该请求）本地后台应用的状态机 `lastApplied` 的值增长到 $\ge readIndex$ 的时候。说明该读取的数据都已安全落入内存。此时直接查内存跳表返回。全程不过日志落盘。

*   **Q2.3 (追问进阶): 如果不用 ReadIndex，有一种更简单的 Lease Read (租约读) 机制，你了解过吗？为什么不选它？**
    *   **思考链条：** 时钟漂移问题 -> 安全性对比。
    *   **回答：** Lease Read 是指 Leader 拿到心跳的多数派 ACK 后，认为在接下来的一个时间窗口（Lease 租约超时时间）内，绝对不会有新的 Leader 产生，因此在此窗口内的读请求，连心跳都不用发，直接查缓存返回，性能比 ReadIndex 更快。**但是我不选它的原因是它强依赖于机器的时钟同步。** 如果由于 CPU 飘移或虚拟机严重卡顿，Leader 本地的时钟慢了，会导致租约判断失效，从而读到脏数据。ReadIndex 依赖的是多数派心跳包的往返消息（逻辑时钟验证），而不是物理时钟，安全性更高。

*   **Q2.4 (极端场景): ReadIndex 能不能跑到 Follower 节点去读分担压力？如果能，会有什么坑？**
    *   **思考链条：** Follower Read -> 取 Leader 的 readIndex -> 同步等待。
    *   **回答：** 可以的拓展。Follower 收到读请求时，自己不能定 `readIndex`，必须去向 Leader 询问当前的最新 `commitIndex` 充当 `readIndex`。拿到之后，Follower 等自己的本地 `lastApplied` 大于等于它再返回。坑在于：如果这根 Follower 所在的网络特别卡，状态机老是赶不上 `readIndex`，就会导致读请求超时卡死。

### 3. 网络模型与并发架构解耦 (C++ 与系统底层)
> **大类说明：** 面试官考察你的工程底层能力（基于 C++）。线程池的设计、Reactor(Epoll) 等网络 IO 知识往往在这里拉开差距。

*   **Q3.1 (架构缺陷分析): 简历提到你引入了业务线程池，如果我不加它，将 Raft 逻辑直接塞在 RPC 的 EventLoop 里会发生什么现象？**
    *   **思考链条：** Epoll 线程模型限制 -> 耗时任务把线程卡死 -> 惊群与全盘超时。
    *   **回答：** 我底层的 RPC 框架是用 Reactor 模型（Epoll）写的。它的核心逻辑是事件循环：发生读事件 -> parse 出完整的 Protobuf 包 -> 回调给上层。**Reactor 线程执行回调的铁律是“必须极快，绝不能阻塞”**。如果我们在回调里继续执行 Raft 的日志同步（比如通过网络等别人回复 `AppendEntries`，或者写磁盘记录状态），当前这根 EventLoop 线程就会陷入阻塞。此时如果有成千上万的其他客户端连接恰好归这个线程管理，那所有的包它都无法及时用 epoll 进行 `read`，最终导致大面积排队超时，拖垮系统。

*   **Q3.2 (池化方案): 引入线程池后，数据的流动是怎样的？你怎么向面试证明这个线程池是“强并发安全的”？**
    *   **思考链条：** 任务投递 -> 队列锁与条件变量 -> RAII 设计。
    *   **回答：** 解耦后：EventLoop 线程只要反序列化出 Protobuf 请求对象，就立即把它和对应的上下文打包成一个 `std::function` (Task)，通过 `enqueue` 放入线程池的任务队列中，随后立马返回去监听新事件。
    *   为了保证线程池安全，我的实现利用了 C++ 的 `std::unique_lock<std::mutex>` 对任务队列的 Push 和 Pop 加锁，利用 `std::condition_variable` 去 `notify_one()` 唤醒处于 `wait` 状态的工作线程。同时，在整个线程池析构的时候，我会设置原子布尔变量 `stop_ = true` 并通过 `notify_all` 唤醒所有线程优雅退出 `thread.join()`，完全利用了 RAII 机制，杜绝因为异常中断忘记解锁或悬挂线程造成的内存泄露。

*   **Q3.3 (进一步深挖 Linux): 你底层 RPC 网络是用什么模型？ET(边缘触发) 还是 LT(水平触发)？如果是 ET 需要注意什么？**
    *   **思考链条：** 边缘触发特性 -> 必须非阻塞死循环读到 EAGAIN。
    *   **回答：** 采用 Epoll，我设置的是 ET（边缘触发）+ 非阻塞 IO。ET 模式只会通知一次状态跃迁（例如从不可读变可读）。如果不搭配非阻塞 IO 并在一次触发内用 `while` 循环把内核 Buffer 里的字节全部读空（直到 `recv` 返回 `-1` 且错误码是 `EAGAIN`），就会漏掉数据。

*   **Q3.4 (多线程边界): 你的 RPC 是在其他线程池调用的回调完成并发给网络线程回复客户端，跨越了线程，这里面的 socket 句柄 fd 会不会已经被关闭了？**
    *   **思考链条：** 连接上下文生命周期 -> `shared_ptr`。
    *   **回答：** 会有这种情况（对端主动断开）。所以我在往任务队列派发 Task 时，底层绑定的 Connection 上下文必须要使用 `std::shared_ptr` 进行智能指针拷贝接管。只要我的业务线程还持有这根句柄生命周期的一个引用计数，底层就不会轻易释放资源。等最后尝试 `send()` 发送发现破损时（触发 SIGPIPE 或返回 -1），才优雅清理。这有效防止了网络模块的 Use-After-Free (悬垂指针) 问题。

### 4. 数据结构选型与生命周期管理 (工程化实践)
> **大类说明：** 考察 C++ 基础数据结构与内存淘汰工程设计的素养。为什么选跳表？TTL 如何避开系统停顿等。

*   **Q4.1 (数据结构选型): 为什么你的状态机选用自研的 SkipList，而不是 STL 原生提供的 `std::map` (红黑树) 或者 `std::unordered_map`?**
    *   **思考链条：** 需求特性(有序性) -> 哈希表对比 -> 并发锁颗粒度。
    *   **回答：** KV 存储业务要求不仅是单点查，往往还包括遍历前缀等操作。`std::unordered_map` 是哈希表且无序，不适用于按区间或者前缀去 Scan 的场景。因此我们需要树状或层级有序结构。
    *   对比红黑树（`std::map`），在多线程并发读写场景，红黑树进行插入删除时往往需要进行复杂的全局旋转进行 `rebalance`，这常常会导致锁着很大一片树结构。而跳表的层级指针插入只影响前后相连的几个节点，不仅更好写代码，而且特别适合改造为基于并发细粒度锁甚至是 CAS 的无锁。工业界如 RocksDB 和 Redis 也大量使用了跳表。

*   **Q4.2 (跳表的细节): 你自己写的跳表，是怎么决定每个节点最高长到第几层的？如何保证 O(log n)？**
    *   **思考链条：** 随机概率 -> 掷硬币函数。
    *   **回答：** 是通过随机函数 `RandomLevel()`。每次插入新节点时，利用像硬币一样抛抛，假设概率 p 为 0.5（或者是二分之一）。如果抛到正面这层数就加一，反之就不往上加。因为这是一个标准的几何分布，期望上，上一层节点数大约为下一层的一半。这使得整个跳表形成了类完全二叉树的层级结构，从而保证搜寻时跨越“立交桥”可以在平均 $O(\log n)$ 内定位目标。

*   **Q4.3 (TTL工程化): 简历中说 TTL “避免了清理导致的长尾延迟毛刺”。假如你有 100 万个 Key 同时过期，讲讲你具体是怎么处理的？**
    *   **思考链条：** 不用全量扫描 -> Redis 借用经验（读时淘汰 + 后台抽样轮询）-> 保护业务。
    *   **回答：** 如果直接用一根定时线程去全表遍历所有的 TTL 配置，当过期键太多时，线程会长期占用全表的读写控制锁，就会导致正常的客户端写请求出现长达几十毫秒甚至几秒的卡顿（就是咱们常说的 P99 / STW问题）。
    *   所以我采用了双重策略（参考了 Redis 的部分思路）：
        1.  **惰性删除：** 用户发来 Get 请求时，先查 TTL 表。如果发现过期了，不仅返回 NotFound，还会顺手“搭便车”向 Raft 集群抛一个 `Delete(Key)` 日志执行真删。
        2.  **后台批量采样：** 单独开启一个非常低频的线程，每隔一定周期（如100ms）在 TTL 池里随机抽取一定数量（比如 1000 个）的 Key 进行探测。如果是过期的直接发清理。如果这 1000 个里过期的占比超过了阈值（比如 25%），说明堆积得太狠，就在本次周期紧接着再来抽样一次。一直降到 25% 以下就停止本周期。这样化整为零，摊薄了 CPU 的毛刺。

### 5. 异常注入与容灾容错测试 (系统兜底能力)
> **大类说明：** 分布式系统不能仅完成“happy path”，需要关注各类灾难演练以及平时是怎么调试代码中这种时序漏洞的。

*   **Q5.1 (宕机重启): 如果服务器重启掉电，内存全丢了，Raft 是怎么恢复跳表里的海量数据的？**
    *   **思考链条：** 日志追加 -> 快照保存 (Snapshot) -> 裁剪丢弃。
    *   **回答：** Raft 平时会将 Leader 下发的已应用 Log 存放到自己的 `Persister` 持久化。重启时读取日志并“一条条 Apply” 即可重构出跳表数据。
    *   但他会面临**日志无限膨胀越来越慢**的问题。所以加入了 **快照日志压缩 (Snapshot) 机制**。只要本地日志量膨胀超过阈值（如若干MB），状态机就会将当前的完整状态打成一个 Snap Block 落盘，同时立刻将这条历史以前的陈旧日志全部抛弃。重启的时候直接 Load 满血版快照，极大地提速。

*   **Q5.2 (容错追踪): 你的简历提到了 Metrics 模块，讲讲在此过程里，你是怎么去测试和 debug 网络分区的脑裂的？**
    *   **思考链条：** 可观测性 -> 隔离测试 -> 定位瓶颈。
    *   **回答：** 我在系统中引入了轻量打点的单例监控：每秒收发条数，当前的角色状态，还有执行延迟 Latency 面板。
    *   **Debug 实战举例：** 为了测试分区问题，我自己手写了一个 Mock 网络层配置：通过命令行指令关闭 Node A 和 C 的物理连接（或者丢包率拉满 100%）。此时通过看板就能肉眼直接看到 Node C 退化疯狂发起提议，Term 往上飙。之后一旦我命令恢复网络连接，就能在这个板子上观察出 `AppendEntries` 开始出现红色的 `conflict` 重新对齐，最终延迟下降到稳态的整个过程。
    *   当初在没有该 Metrics 的时候，我经常碰到 Client 说超时了，但后台没报错，就是不知道死哪了。有了数据统计后，我发现了自己旧版在“共识不决等待”阻塞 EventLoop 这件事。它真真切切帮我锁定了需要优化线程池的核心线索。

## 三、 真实环境性能调优与单机极限压测记录（实战测试篇）

> **服务器环境背景**：2 核 CPU / 1.6GiB 内存 / 无 Swap / 40G 机械硬盘 (HDD: ROTA=1) / 最大句柄 65535。
> **测试哲学**：利用拉胯的物理配置（特别是 HDD 和小内存），能极其容易地放大并观察到分布式存储引擎的 IO 瓶颈与内存泄漏，从而展现架构调优的价值。

### 阶段一：机械硬盘慢 I/O 带来的写阻塞与 Raft 选举毛刺 (压力写测试)
**1. 测试目的**：观测原生 Raft 频繁写盘（Persister）在 HDD 上的严重性能受限，证实为何要将 Raft 同步从网络主线程（EventLoop）中剥离。
**2. 执行操作**：
*   **启动服务端**：利用 `./raftKvDB` 启动 3 节点集群。
*   **模拟高频客户端打流**：编写或利用 Shell 循环多次调用 `./callerMain` 疯狂发送 Put 请求。
*   **观测命令**：
    *   使用 `iostat -d -x 1` 监控 vda 磁盘。重点观察 `%util` (磁盘使用率) 和 `await` (IO等待时间)。
    *   使用 `top` 观察 CPU 所在行的 `wa` (IO Wait) 指标，并看会不会引发 CPU 资源被拉空。
**3. 预期现象**：由于 HDD 的随机写 IOPS 极低，大量的 Put 将导致 `vda` 的 `%util` 瞬间飙升至 100%，大量线程将卡在落盘调用上，甚至可能由于单次刷盘超时导致 Raft 心跳没能及时发出去，引发偶发的异常切主（Leader Election）。

### 阶段二：ReadIndex 在慢磁盘环境下的“降维打击”对照测试 (纯读测试)
**1. 测试目的**：验证引入 ReadIndex 后，纯获取操作是否成功避开了拉胯的机械硬盘，从而实现性能的颠覆性提升。
**2. 执行操作**：
*   在大量数据 Push 完成后，只执行 Get 逻辑的压力验证。
*   **观测命令**：同样保持开启 `iostat -d -x 1`，同时监控客户端侧计算出的 500 次 Get 循环的总耗时。
**3. 预期现象**：开启 ReadIndex 时，`Get` 操作阶段磁盘的 `%util` 应该一直保持在极低水平（0%～5%），因为无需生成占位 Log 并落盘；客户端 Latency 实测值应明显低于退化回写盘的传统一致性读。

### 阶段三：1.6G 极小内存下的 OOM 危机与 TTL 兜底测试
**1. 测试目的**：验证系统应对海量 Key 时的内存储备情况，证明 TTL 惰性删除加后台抽样的工程意义。
**2. 执行操作**：
*   准备包含大量 Key 的 Put 压测写入（可以设置短暂的 TTL 如 5s）。
*   **观测命令**：
    *   另起终端使用 `watch -n 1 free -m` 实时观看 `available` 内存的下探速度。
    *   配合 `ps -eo pid,pmem,rss,cmd --sort=-pmem | grep raftKvDB` 观察这三个独立进程的 RSS（物理内存驻留）增长曲线。
**3. 预期现象**：如果没有 TTL 或者清理机制失效，1.6G 内存在抛弃大量无效的历史状态机 KV 后会很快见底触发系统 Kill。伴随偶尔对全表的随机 `Get` 触碰和后台定时抽样，我们可以看到进程内存 RSS 的增长出现明显的“波浪形”刹车，不再出现不可逆的雪崩。
