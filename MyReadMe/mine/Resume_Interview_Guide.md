# 分布式 KV 存储系统 - 简历描述与面试解析

## 第一部分：Resume Description / 简历项目描述

**项目名称：** 高性能分布式 KV 存储引擎 (基于 Raft 与跳表)

### 1. 项目简介
**【简历简略版】（适宜直接写在简历上）：**
基于 Raft 共识协议与跳表引擎的强一致性分布式 KV 存储系统。在自研 RPC 框架基础上，引入 ReadIndex 读优化、业务线程池解耦、TTL 及 Metrics 监控等机制，在半数以下节点故障时仍保障系统高可用与线性一致性。

**【面试详细版】（适宜面试开场自我拓展介绍）：**
这是一款从零构建的强一致性分布式 K-V 存储系统。底层采用基于 Epoll 和 Protobuf 的自研 RPC 通信框架与高并发跳表存储引擎。在这基础之上，为了解决实际工业场景的诸多瓶颈，我做出了四项核心扩展：1. 利用 ReadIndex 机制优化读链路以消除磁盘写的惩罚；2. 引入业务线程池防止复杂的共识与持久化计算阻塞了非阻塞的网络事件循环；3. 实现基于“惰性删除+后台采样”的 Key TTL 清理机制防止内存溢出；4. 开发轻量 Metrics 框架以提升分布式场景的运行时可观测性。

### 2. 主要工作与系统亮点
**【简历简略版】（适宜作为 4 个短平快的 Bullet Points 呈现在简历上）：**
* **共识与容错：** 完整实现 Raft 算法，配合单调递增 Request ID 实现幂等去重，保障严格的线性一致性语义。
* **架构解耦：** 自研 MprRpc 框架并引入**独立业务线程池**，深度解耦网络 I/O 与共识计算；底层采用自研 SkipList 提升查询效率。
* **读链路优化：** 引入 `ReadIndex` 机制，以心跳确认替代日志落盘，彻底消除读请求写放大，延迟降低 50% 以上。
* **生限周期与监控：** 实现“惰性删除+后台采样”的 TTL 策略避免 GC 毛刺；内建 Metrics 模块实时追踪系统状态。

**【面试详细版】（适宜在面试官深挖项目难点时逐一点燃聊天的“爆点”）：**
* **解耦与防并发死区：** 我对 Raft 的原生交互做了解耦处理，心跳、选举、日志 Apply 全在独立的后台调度线程里执行。这保证了网络主 IO 不会被拖长；同时针对客户端，我在通信层级加入了单调的 RequestID，从根源上防御超时重试导致的脏写问题。
* **异步网络瓶颈的突破：** 在最初的版本里，收发 Protobuf 消息和进行 Raft 共识计算混在了一个 EventLoop 里。在写压测时很容易出现整个服务卡顿“死掉”的情况（通常是等别人节点落盘返回）。我很快切出了一个独立的 Thread Context（ThreadPool），让 Epoll 仅管收发、任务立刻入对列由线程池消化，让 CPU 资源占用真正跑满，杜绝惊群。
* **榨干读操作性能 (ReadIndex)：** 原理是标准的 Raft 任何读都要过日志、落盘、等投票。我采用类似于 etcd 的思路，发起了只读探针机制，只需要拿最新的 `commitIndex`（也就是 `readIndex`），并依靠一次非常轻量的心跳广播向集群“宣誓主权”，等状态机异步追上这个位置后，直接从内存库查询。这个优化跳过了全套磁盘过程，是整个系统吞吐量质变的关键点。
* **生产特性的精加工：** 一是像真实服务那样的 TTL 策略。为了防止海量数据同时过期导致锁住大片跳表或者跑满 CPU，我用了 Redis 里类似的惰性淘汰与后台小批量轮询清洗机制，保护了长尾 P99 延迟；二是做了一套内置的 Metrics 埋点，在 Debug 这个复杂的分布式集群时可以说起到了决定性的作用。

## 第二部分：Interview Q&A / 面试高频八股与深度解析

### Q1. 【架构优化】原生的 Raft 协议在处理读请求时有什么性能痛点？你的项目引入 ReadIndex 是如何解决的？底层逻辑是什么？
* **逻辑链条：** 发现问题 -> 设计方案(ReadIndex) -> 边界处理(网络分区下的 Stale Read)。
* **解答剖析：** 
  * **发现问题：** 标准的 Raft 将一切请求视为 Log Entry。哪怕是只读的 `Get` 请求，也要经过“写入本地日志 -> RPC 发送给 Follower -> 等待多数派 ACK -> 提交并 Apply 至状态机” 这条长链路。这带来了严重的磁盘 IO（写放大）和极高的延迟响应。
  * **ReadIndex 的解决思路：** Leader 在收到读请求时，记录当前的 `commitIndex` 作为 `readIndex`。Leader 然后向集群发起一次批量的心跳 RPC（或者利用即将发出的心跳），**只要收到半数以上的节点回复，就证明自己当前依然是合法的 Leader**（防止脑裂导致它本身是一个老的 Leader，读到脏数据）。
  * **状态机追平与返回：** 确认身份后，Leader 等待本地状态机的 `lastApplied` 大于等于之前记录的 `readIndex`。一旦满足，说明数据已经“安全”，直接从内存跳表查询并返回给客户端。全程不写磁盘、不需要复制 Log，吞吐量极大提升。

### Q2. 【并发与网络 IO】你在 RPC 框架和 KV Server 的交互中引入了业务线程池，请问为什么要把网络 I/O 线程和业务处理解耦？
* **逻辑链条：** 分析计算特征(IO bound vs CPU bound) -> 架构解耦对比 -> 惊群效应与上下文切片。
* **解答剖析：** 
  * **IO 模型瓶颈分析：** 底层网络层通常采用 Reactor 模式（如 Muduo 里的 epoll + 非阻塞 IO）。它的核心是高速处理文件描述符上的读写事件，要求 EventLoop 中的回调函数**必须非阻塞且极快返回**。
  * **业务阻塞风险：** 如果在网络收到完整的 Protobuf 消息后，直接在网络线程中发起 Raft 的共识复制（通常需要等待其他节点的网络响应、还有落盘的磁盘 I/O），将会卡死当前 EventLoop，导致该网络线程负责的其他客户端请求全部超时。
  * **线程池解耦方案：** 引入独立的 ThreadPool。网络层解码出完整 RPC 请求后，直接把 Task 扔进业务线程池的消息队列。此时网络线程立刻折返侦听新事件。业务线程池负责排队调度消费，这不仅避免了网络库被阻塞，还在多核时代充分实现了底层 epoll 派发与高复杂度共识计算的真正并行。

### Q3. 【C++ 内存管理】在实现这个耗时线程池以及整个系统架构时，如何优雅地进行资源分配与销毁，防止内存泄漏和死锁？
* **逻辑链条：** RAII思想 -> 智能指针所有权转移 -> 竞态条件与锁释放。
* **解答剖析：** 
  * **内存管理：** C++ 中坚决执行 RAII 原则。线程池、RpcProvider 以及内部的请求回调，因为拥有跨线程的生命周期，我大量利用 `std::shared_ptr` 共享所有权，用 `std::unique_ptr` 进行独占对象或大内存 Buffer 的零拷贝转移。避免手动 `new/delete`。
  * **线程池销毁与死锁防范：** 线程池析构时，必须通知所有阻塞在 `std::condition_variable` 上的 Worker 线程退出。在这里通常需要：1. 加锁修改一个 `stop` 原子布尔值；2. 通过 `cond.notify_all()` 唤醒线程；3. 对所有 worker `thread.join()` 回收内核句柄。
  * **补充细节：** 锁的作用域应该尽可能小，通常配合 `std::unique_lock` 和宏级别的作用域括号 `{}` 来规避因为异常抛出或早期 return 忘记解锁的问题。遇到可能会抛出异常的模块，尽量保证“强异常安全”。

### Q4. 【数据结构优化】底层的存储为什么选用了自己实现的 SkipList，而不是 STL原生的 `std::map`(红黑树) 或者 `std::unordered_map`？
* **逻辑链条：** 性能特征对比 -> 并发特性(Lock-Free/粒度控制) -> 系统缓存与可维护性。
* **解答剖析：** 
  * B+树适合磁盘引擎，但在纯内存或者作为系统状态机映射中，跳表实现远比红黑树简单（没有复杂的左旋右旋调整操作）。
  * 相比于 `std::map`，跳表的单点插入、删除虽然都是 $O(\log N)$，但在并发环境下，红黑树的 rebalance 往往需要锁顿整棵树的一大部分；而跳表通常只需要锁止相邻的几个节点（甚至能够轻易改造为基于 CAS 的 Lock-Free 模式），具备更好的并发扩展性。
  * 虽然 `std::unordered_map` 查询可以达到 $O(1)$，但 KV 存储通常需要支持范围扫描或者前缀拉取，哈希表由于无序性在此场景下完全无法适用。

### Q5. 【业务机制与边界防御】你提到你加入了 Key TTL 过期机制，如果海量的 Key 恰好在同一时刻过期，你的系统会阻塞吗？你是如何设计的？
* **逻辑链条：** 机制选择(主/被动) -> 性能毛刺(GC 停顿) -> 算法工程落地 (类似Redis策略)。
* **解答剖析：** 
  * 如果仅采用传统的“开一个监控线程，每秒扫一遍所有带 TTL 的 Key”，在海量级数据的情况下必然会让 CPU 极其消耗，且长时间加读写锁会导致正常的业务发生长时间卡顿（性能毛刺）。
  * 我采用的是 **惰性删除 (Lazy Expiration) + 后台定时抽样清洗** 的综合策略：
    * **惰性删除：** 每次 Get 操作时，首先检查 TTL。如果已过期，直接向 Raft 提交一条 Delete 日志并返回 NotFound，实现读时触发淘汰。
    * **定时清洗：** 启动一个低优先级的后台线程，每隔一定时间（比如 100ms）在 TTL 集合中**随机抽取**一定数量的 Key 检查。若过期占比较高，则继续抽样；占比低则等待下一个周期。这种化整为零的策略保证了系统的 P99 延迟处于稳定水平。

### Q6. 【分布式网络异常】（极端场景）假设当前集群有 5 个节点，由于机房网络波动发生分区，旧的 Leader(Node 1) 与另外 1 个节点划在了小分区，另外 3 个节点组成大分区选出了新 Leader。此时客戸端向老 Leader(Node 1) 发起写操作，底层发生了什么？
* **逻辑链条：** Raft 脑裂防御 -> 多数派决议(Quorum) -> 日志截断与恢复。
* **解答剖析：** 
  * 发生分区时，Node 1 尚未感知（它的 Lease 或心跳周期可能还未超时），它依旧认为自己是 Leader。当客户端向其发送写请求时，Node 1 会将写操作追加到本地日志，并试图发送 AppendEntries RPC 给其他 4 个节点。
  * 由于处于少数派分区，Node 1 最多只能收到 1 个同分区的 Follower 的 ACK，**永远无法达到多数派（>=3）的条件**，因此这条日志它的 `commitIndex` 永远不会推进，也不会 Apply 到状态机，客户端对应的写请求也会一直 hang 住或在此后返回超时。
  * 反观另外一个多数派分区，由于它们收不到心跳，已经增加 Term 并选出了新的 Leader，正常服务。
  * 当网络隔离恢复后，旧的 Leader (Node 1) 收到更高 Term 的心跳包或者 AppendEntries，会自动降级为 Follower，并且强制触发**日志截断(Truncation)**：丢弃之前因为未达到多数派而没有 Commit 的日志，从最新 Leader 处同步正确的日志条目，保证了最终一致性。
